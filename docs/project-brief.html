01 / Product & scope

A finance assistant that notices the moment to help

The user should be able to begin ordinary work in NetSuite and receive a timely, useful offer from an assistant that understands the surrounding browser workspace.

The hackathon showcases Astra’s ability to interpret application context, reason across multiple sources, operate browser interfaces, and produce a reviewable result. The first workflow is vendor bill discovery and preparation within the broader finance close process.

Agreed

Initial scope

A Chrome extension in a dedicated profile, a selectable workspace of watched tabs, ambient suggestions, and an investigation across a real NetSuite sandbox and demo Gmail account. A Google Sheet of onboarded vendors is optional.

Scope boundary

Keep the first demo focused

Build one complete workflow before expanding to the entire close. Hosted deployment, application connectors, application OAuth integrations, and a general library of finance workflows are outside the initial plan.

All interaction with Gmail, NetSuite, and the optional Sheet uses their browser interfaces and existing logged-in sessions. The application supplies the browser tools; Astra chooses and interprets their use. The model API does not automatically have access to local tabs.

02 / Demo narrative

From “Add New Bill” to a prepared entry

  1. Select the close workspace.

    The user chooses the NetSuite sandbox, demo Gmail inbox, and optionally the vendor-onboarding Sheet. Watched pages display a small status icon.

  2. Begin normal work in NetSuite.

    The user opens “Add New Bill.” The extension recognizes the form and captures relevant context, including a selected vendor if available. The actual sandbox’s labels and page structure still need inspection.

  3. Offer a contextual investigation.

    A small bubble asks: “Check Gmail for invoices that need recording?” The user can accept or dismiss it without opening a separate application.

  4. Investigate across the selected tabs.

    Astra searches Gmail for relevant invoice messages, inspects invoice information, checks NetSuite’s existing bills, and consults vendor onboarding where that source is present.

  5. Present findings with evidence.

    Show candidates, matching records, amounts and dates where verified, source links, and any remaining ambiguity. A useful seeded scenario contains an already-recorded invoice, a candidate without a matching bill, and an invoice whose vendor needs onboarding.

  6. Offer to prepare a selected bill.

    The user selects a candidate. The agent fills the relevant form fields and verifies the result. The prepared entry remains ready for the user’s review before submission.

Evidence matters. “No match found in the records checked” is different from proving that a bill does not exist. Findings should preserve the search scope and distinguish invoice matching from vendor-onboarding status. The example outcomes above are proposed demo data, not findings from the real accounts.

04 / Architecture

Local control, model-powered decisions

GmailMessages & invoice evidence

↕ model requests, selected observations, and tool results
OpenAI API · AstraRemote inference; API credential stays in the local backend

Gmail, NetSuite, and Sheets are remote applications viewed through Chrome. “Local” describes our application runtime and storage, not offline operation.

The backend owns agent runs and durable state. The extension executes permitted browser operations and returns observations. A disconnected extension must reconnect to a known task state rather than silently losing the run or replaying prior actions.

Why the Agents SDK

The agreed choice is a purpose-built agent using the OpenAI Agents SDK in TypeScript. It provides the agent loop, tools, tracing, session support, and resumable run state. Codex app-server was considered for reusing a broader coding-agent runtime, but the current project centers on browser workflows and a custom product experience. A direct Responses API loop remains possible but would require more orchestration code.

Our browser bridge is required with any of these harnesses. Astra supports custom UI tools; the official computer-use guidance recommends code execution for Astra. We will begin with a small typed tool surface, then consider a constrained code-execution runtime if the demo needs richer action sequences. Such a runtime is not assumed to be included in the first build.

05 / Ambient operation

Continuous awareness through meaningful events

The ambient experience comes from lightweight page observers and short, purposeful agent runs. Page navigation, entry into a bill form, and vendor selection update workspace state. The backend evaluates useful changes and decides whether to stay quiet, refresh a suggestion, or offer a new task.

Observe → summarize context → evaluate usefulness → suggest → act when accepted → verify

Local observation

Detect relevant page transitions and form context, debounce bursts of changes, and attach a page version. Keep ordinary DOM churn out of the conversation. Send compact observations when they matter.

Model judgment

Interpret the current workflow and prior interaction. Return a structured decision: no suggestion, update an existing suggestion, or present a new one. A pending suggestion does not itself authorize a takeover.

  • Remember dismissals. Use cooldowns and context-aware deduplication so the same offer does not keep returning.
  • Ignore self-generated triggers. Agent actions should not create a loop of new ambient suggestions.
  • Discard stale decisions. If the user leaves the form while a suggestion is being generated, re-evaluate its relevance before displaying it.
  • Separate watching from acting. Ambient evaluation observes; an accepted task can request the browser controls needed for its scope.
  • Report real state. Paused, disconnected, and working should be distinguishable. Background tabs can be throttled or discarded, so the interface should not claim perfect continuous observation.

Chrome’s extension service worker is event-driven and may stop when idle. We will persist needed state and use reconnectable messaging, with the ongoing agent task owned by the backend.

06 / Sessions & delegation

One workspace coordinator, focused task histories

State layerContentsPurpose
Workspace stateSelected tabs, latest context, page versions, monitoring preferences, active task IDs.Keep an up-to-date picture outside the transcript.
Coordinator historyUser conversations, useful context summaries, suggestions, dismissals, accepted work, summarized findings.Maintain one coherent assistant presence per workspace.
Task historyDetailed searches, screenshots, invoice evidence, comparisons, tool calls, and form actions.Support a bounded investigation and later continuation.

When the user accepts a suggestion, the backend creates an investigation task with an explicit goal and permitted workspace. It receives the relevant context, performs the work, and returns structured findings to the coordinator. The coordinator preserves a summary and task reference; the detailed history remains available when the user asks to prepare a bill.

The SDK supports sessions and agents-as-tools, allowing a main agent to retain control while invoking a specialist. The application must implement task IDs, parent-child relationships, storage, and continuation rules. These relationships are not automatic “subsessions.” Start with one coordinator and one bill-investigation agent; add specialists when they need meaningfully different tools or responsibilities.

Concurrency rule: one agent controls the browser within a workspace at a time. Serialize changes to coordinator history. On cancellation, stop scheduling browser commands, discard queued actions, and reconcile any action already in flight before resuming. A click already delivered to a page cannot be retroactively cancelled.

08 / Browser contract

The interface that lets both developers move independently

Agree on the first schemas before building either side deeply. The extension owns execution; the backend owns intent and interpretation. Tool names below are illustrative contracts to finalize together.

Message familyExamplesImportant fields
Context eventPage changed, bill form opened, vendor selected.Workspace, tab, event ID, observed time, page version, relevant context.
Browser commandList tabs, inspect page, click, type, capture screenshot.Command ID, task ID, workspace, target tab, expected page version, validated arguments.
Tool resultObservation, screenshot, completed input, explicit failure.Matching command ID, success/error status, current page version, observation.
UI eventSuggestion, progress, finding, review request, stopped.Workspace/task association, visible content, evidence references, available user actions.

Operational rules

Validate workspace membership and current page state at execution time. A browser command needs a clear result, including errors. Do not blindly replay clicks or form submissions after a reconnect; use command IDs and outcome checks. Retain references to the observations behind each finding so the user can inspect the source.

The browser bridge will need real-page testing for NetSuite form controls, Gmail search and invoice attachments, frames, and the optional Sheet. A generic “click” tool alone is not a complete application integration.

09 / Local development

Each computer runs a complete local application

Install the unpacked extension only in the prepared demo Chrome profile. Run the Node backend and SQLite database locally. Keep the OpenAI API key in backend environment configuration excluded from Git. NetSuite and Gmail use the profile’s own logins.

Local to each developer

Extension installation, browser profile and cookies, API credentials, pairing token, SQLite database, and task artifacts. Bind the backend to 127.0.0.1 and pair the extension with a local token and origin checks.

Shared through Git

Application source, shared schemas, setup instructions, reproducible test fixtures without account contents, architecture documents, and coordination updates. Sharing code does not share a running browser session.

No hosted application accounts or Gmail/NetSuite OAuth integration are needed for the initial demo. Astra still runs through the remote OpenAI API, and the selected observations supplied to it leave the machine. SDK tracing should be explicitly configured with that data flow in mind.

12 / Validation & unknowns

Test the parts the real accounts will decide

The initial prototype passes 14 tests, type checking, and a production build. Astra completed a read-only inspection of the actual NetSuite Home dashboard through the paired extension. The main uncertainties are bill entry, Gmail and attachment interaction, and ambient suggestion timing. Consult the implementation’s validation record for the precise coverage and remaining checks.

QuestionFirst verification
Can we recognize the bill screen?Inspect the sandbox’s real route, form structure, vendor field, frames, and transitions.
Can we read the invoice evidence?Try the demo Gmail searches and representative attachments; identify browser rendering or download handling required.
What counts as a plausible duplicate?Agree on comparison fields and search scope; include vendor, invoice number, dates, currency, and amounts where available.
What does the vendor sheet contain?Confirm whether it is included and inspect its columns, status meanings, and readable browser representation.
How should ambient suggestions behave?Exercise dismissals, repeated visits, vendor changes, workspace switches, and user navigation during evaluation.
Can tasks stop and resume safely?Interrupt during reads and form filling; disconnect the bridge; verify that completed actions are not replayed.

Implementation principles

Enforce selected-workspace boundaries in code. Treat page and email content as evidence, not instructions that can expand the task. Keep source references and use deterministic calculations. Keep bill submission as a deliberate user review step. Verify effects in the application rather than trusting a model’s claim that an action succeeded.

Outstanding decisions

Record the teammate’s prototype branch; validate the actual bill and Gmail pages; confirm the optional Sheet and demo invoice set; define a default search period; and compare prototype behavior. Package versions, API access, and initial workspace/history behavior are established in Ambient and can evolve after the comparison.
